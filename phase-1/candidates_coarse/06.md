# 『Sustainable Web Development with Ruby on Rails』を読んだ感想

Railsの設計で頭を抱えた経験のある人なら、うなずいたり反発したりしながら楽しめる本でした。Web開発を長く生き延びてきた人が語る定石、という手触りがあります。

Railsの設計本というと、きれいな原則を示してそれに従えという形のものが多い印象ですが、この本はそうではありません。そのあたりも含めて紹介していきます。

## 著者と本の構成

著者はStitch Fixでプログラマからアーキテクトまで務めた後、別のスタートアップでCTOを務めている方です。『Agile Web Development with Rails 6』の共著者であり、Brutalist Web Designのサイトの主でもあります。Javaから入ったキャリアが、この年季の入った感じの出どころかもしれません。

全体は3部に分かれています。

- 導入

- Railsの各部分の使い方を細かく論じる本編

- Rails本体から離れた話（認証と認可、API、CI、監視やログといった運用）

本編がRailsの各部分の使い方を細かく論じる形になっているのが特徴で、設計の話だけを抽象的に語る本ではありません。

## 「持続可能」とは何か

タイトルにある持続可能性とは何なのか、という話が最初に出てきます。

ここで言う持続可能性は、仕様や使えるリソースが増減したり入れ替わったりしても、チームの顔ぶれが変わっても開発を続けられること、とされています。規模や速さの話ではないので、スケーラブルという語は避けたらしいです。この言葉選びには納得がいきます。

著者はクリーンアーキテクチャやSOLIDに与しないことをはっきり示しています。そして、オブジェクト指向らしさ、エレガントさ、再利用、デザインパターン、メトリクスといった言葉で何度も痛い目を見たと打ち明けたうえで、読みやすさと直しやすさを代わりに掲げます。

この告白の部分は本の中でも何度か出てきます。ここまで書くからにはそれなりの経験があったのだろうと想像しますが、とはいえ極端な教条に走ることはなく、どれも引き換えの関係だと繰り返しています。あれは駄目だこれは駄目だという話にはなっていないわけで、このバランスの取り方が本全体の調子を作っています。

つまり、あるべきアーキテクチャを突き詰めるのではなく、目の前の課題を片付けつつシステムを無事に育て、開発を続けられることに重きを置いているわけです。

## Railsとの付き合い方

Railsの良さは目一杯認めて寄り添いますが、全面的に従うのではなく、取るものと捨てるものを選んでいます。そして、格好いい手法や新しい手法ではなく、年季の入ったやり方を選びます。

Railsを捨てて別の何かを持ってくるのでもなく、Railsに全部任せるのでもない、という立ち位置です。このあたりが読んでいて一番おもしろいところでした。

レールから外れる箇所の例としては、

- データの整合性はActiveRecordの検証ではなくDBの制約で担保する

- マイグレーションをRubyでなくSQLで書く

- ActiveJobを介さずジョブのライブラリを直に使う

- コールバックやHelperは用途を絞る

などがあります。どれも、言われてみれば理屈は分かるものの、Railsらしいやり方とは言いにくいものです。

細かい方針としては、例にOpenStructをよく使う、CSSはデザインシステムを前提にOOCSSかユーティリティ系を選ぶ、ログはLogrageで1行にまとめる、テストにはMinitestとFactoryBotを使う、テンプレートはERB、Rakeタスクを1つずつ別ファイルに置く、といったものが並びます。これらは好みの問題という面もありますが、選んだ理由がその場で語られるので、読み飛ばさずに追っていけます。

## サービスクラスと層

本の中心にあるのは、ドメインのロジックをActiveRecordやActiveModelには書かず、サービスクラスとそれを置く層に移す、という方針です。コントローラやジョブ、メーラからActiveRecordに直接触らないのが原則になります。

Railsでサービスクラスというと議論になりがちな話題ですが、この本ではそこがかなり踏み込んで書かれています。

モデルから業務のロジックを引き剥がす理由は、次のような筋で説明されます。業務のロジックは複雑で変わりやすく、そういうものが各所から頼られるとバグが重くなりシステムが揺らぐ。一方で、ActiveRecordのモデルは各所から参照されるのを避けられない。だから両者を同じ場所に置いてはいけない、というわけです。

モデルが太るからよくない、という言い方で済ませていないところが良いと思いました。何がどう困るのかがはっきりしているので、どこまで分ければよいのかも考えやすくなります。

ここで注意したいのは、ActiveRecordを薄くして何も書かないようにする、という話ではないことです。一方でassociationは書きますし、画面向けと割り切った検証も普通に書きます。なので、ActiveRecordは使い勝手のよいデータアクセスの層として残り、共通化したいクエリもそこに書かれます。

つまり、ActiveRecordを別の何かで置き換えようとはしていません。業務のロジックだけを外に出す、という線の引き方です。

結果として、ドメインのロジックの層がデータアクセスの層に依存する向きになっていて、クリーンアーキテクチャとは逆です。見方を変えれば、PofEAAの頃へ引き返したような印象もあります。もっとも、著者はクリーンアーキテクチャに与しないと宣言しているので、これは筋が通った話です。Rubyは融通が利くのでそこまで依存の注入に凝らなくてよい、というのも分かる気がします。

サービスクラスの作法も細かく書かれています。

- クラスメソッドではなくインスタンスを作ってから呼ぶ

- callのように何にでも使える名前は付けない

- 外から全部注入するのではなく、必要ならメソッド内で作る

- 戻り値はそのサービス専用の結果クラスで包む

といった具合です。細かいと言えば細かいのですが、どれについても、なぜそうするのかをその場で具体的に述べています。なので、読者は納得できるかどうかで取り入れるかを決められます。ここが大事なところで、こうしなさいとだけ書かれていたら、従うか無視するかの二択になってしまうところでした。

この結果クラスについては、汎用のResult型のようなものを想像すると全然違います。そういう名前が出てくると型の話かと思ってしまうのですが、そうではありませんでした。現場で練られた知恵という感じで面白いところです。

なお、この本の言うサービスクラスは、結局ただのRubyのクラスです。それを置く場所をサービス層と呼んでいるだけなので、身構えなくてよいと思います。Rails標準のクラスだけで粘らず業務のロジックを分けてテストも書こう、共通の親クラスを無理に作らなくてよい、という穏やかな話です。ただし自由度が高く、自分たちで規則を作らないと統制が取れないのが難しいところではあります。
