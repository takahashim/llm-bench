# tailwindcss-railsが今の形に落ち着くまで

## Tailwind CSSについて

Tailwind CSSはUtility-Firstを掲げるCSSフレームワークです。見た目の指定がそのままタグのclass属性に長々と並ぶ、というのが最大の特徴になります。

これはこれまでのCSS設計の定石とはほぼ逆を向いています。CSSは見た目の指定をHTMLから引き剥がすためのものだったはずで、そう考えてきた人からするとかなり落ち着かない話です。実際、OOCSSやBEMを使いこなしてきた人ほど、HTMLに埋め込まれた記法に面食らっていたようです。せっかく名前の付け方を工夫してきたのに、それを全部やめようという話に見えるわけですから、面食らうのも当然ではあります。

とはいえ、そうなった事情もあります。ReactやVueの広まりでCSSの命名規則にコンポーネントの事情を背負わせなくてよくなり、不要な定義を削る仕組みで本番のCSSを小さくできるようになった、という流れです。命名を工夫する理由と、書いたものが全部残ってしまう理由の両方が薄くなった、ということになるのでしょう。

つまり、これまでの定石が解いていた問題を別のところで解いてしまったので、その定石を手放せるようになったわけです。好き嫌いや現場の都合はあれど、一定の支持は得ているのではないかと思います。

なお、ここで出てきたコンポーネントという話はRails側にも関わります。Railsのテンプレートでコンポーネントを扱う場合は、このところはViewComponentが選ばれていることが多い印象です。

## RailsでTailwindを使う

tailwindcss-railsは、DHHが2021年1月に着手したgemです。v1.0.0の正式版が出たのは日本時間で12月15日で、その翌日にRails 7が公開されています。つまり、Rails 7に合わせて仕上げられたものだと見てよさそうです。

それ以前にTailwindをRailsへ持ち込む手立てとしては、

- WebpackerやSimpackerと組んでnpmで入れる

- フロントエンド側のフレームワークに任せてRails側は手を出さない

- CDN上のものを読む

といったあたりでした。どれも、できないわけではないのですが、Railsだけで話を済ませたい人には重かったり物足りなかったりするものです。前の2つはNode.jsまわりの面倒を引き受けることになりますし、最後のものは本番で使うには心もとないところがあります。

そして、Rails 7はConceptual Compressionを押し進めていて、Node.jsなしでもRails自身で片が付くように、新しいgemの整備が進められてきました。tailwindcss-railsもその一環ということになります。

つまり、このgemはただTailwindを入れやすくするためのものというより、Rails 7が目指しているものの一部だと見た方が分かりやすいと思います。そう考えると、後で書く経緯もなぜそうなったのかが見えてきます。

## 12月に起きたこと

ところが、12月20日の時点では、このgemはv2.0.2まで進んでいました。正式版が出てからまだ1週間足らずのことです。メジャーバージョンが上がった上にパッチが2つ出ているわけで、短い間に状況が大きく動いたことになります。せっかくなので経緯を追ってみます。

まず、12月10日に出たTailwind CSS v3.0では、v2.1で入ったJITエンジンが既定となりました。これによって、Node.jsなしでは実際上使いにくいものになっていました。

Rails 7の公開はその6日後なので、タイミングとしてはかなり厳しいところです。本体の新しいバージョンが出て、しかもそれがNode.jsを必要とする方向に寄った直後に、Node.jsを外したいgemの正式版を出すことになったわけです。

そのため、12月15日のv1.0.0はTailwind CSS v2.1向けという位置づけになります。v3を今すぐ使いたければ、cssbundling-railsと組み合わせてNode.jsに頼るしかありませんでした。

しかしNode.jsに頼る状態は、先に書いたRails 7の方針と噛み合いません。それならgemを独立させた意味がなかったのでは、という話になりかねないところでした。せっかくRails本体の側でNode.jsを外しにかかっているのに、肝心のところで戻ってきてしまうわけです。

もちろん、v2.1のままで使うという選択もあったはずです。ただ、本体が先に進んでしまっている状態でそれを続けるのは、やはり気持ちのよいものではありません。

ところが、ここで動いたのはgem側ではなくTailwind側でした。12月17日に、Tailwind公式がStandalone CLIを打ち出しました。RailsやPhoenixといったnpmを前提としない環境でも、性能を落とさず使えるようにするためのものです。Rails側の都合だけの話ではなかったようです。

Standalone CLIの実体は、JITエンジンをNodeの処理系ごと1本の大きなバイナリに固めたものです。RubyのExerbやTraveling Rubyに近いと言えます。つまり、Node.jsがなくなったわけではなく、見えないところに押し込められただけです。素直にNode.jsを使っているじゃないかと言いたくもなりますが、npm周りの作業が消えるのは確かに楽です。入れる側からすれば、バイナリを1本置けば済むのと、package.jsonから面倒を見るのとでは、やはりだいぶ違います。

そしてgem側では、12月18日にCLIを取り込む変更が入り、同じ日に2.0.0が公開されました。CLIが出た翌日ということになります。このとき、v1.0.0にあった不要なCSSを削るRuby側の処理は、CLIに任せられるので丸ごと取り除かれています。やることが減ってgemが小さくなったわけで、こういう変化は気持ちがいいものです。

## おわりに

出てきた当初は、便利そうでも強引さを感じるところがありました。かつてRailsで流行っては消えた、JSをgemで包む手法も頭をよぎりました。ああいうものは、最初は便利なのですが、本体の更新に追いつかなくなって捨てられるのが相場です。

それがStandalone CLIの出現で、安心して使えるものに生まれ変わったように見えます。わずか数日のことなので、追いかけていた側としてはずいぶん慌ただしい思いをしました。

ちなみに、Standalone CLIが内部で使っているpkgはVercel製です。Node.jsのフロントエンド文化を引っ張ってきた会社が、Node.js抜きの環境づくりにも効いているというのは、思いがけない巡り合わせだと感じました。もちろんそういう意図で作られたものではないのでしょうけれど、道具は作った人の思惑とは違うところで役に立つものです。

今後は仕組みから考えて、Tailwind CSS本体の更新に追従する形で、このgemもリリースされていくことになると見られます。CLIをそのまま持ってくる作りになったので、gem側で独自にやることはあまりありません。追従が早いのはありがたい話ですが、バージョンの対応関係には気をつけておく必要がありそうです。
