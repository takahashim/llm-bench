# 『Sustainable Web Development with Ruby on Rails』を読んだ感想

『Sustainable Web Development with Ruby on Rails』を読みました。Railsの設計で頭を抱えた経験のある人なら、うなずいたり反発したりしながら楽しめる本だと思います。Web開発を長く生き延びてきた人が語る定石、という手触りがあります。読んでいて全面的に賛成できるかというとそうでもないのですが、賛成できないところも含めて楽しめる、という種類の本です。

その手触りはどこから来ているのか、と思って著者の経歴を見てみると、なるほどという感じでした。著者はStitch Fixでプログラマからアーキテクトまで務めた後、別のスタートアップでCTOを務めています。『Agile Web Development with Rails 6』の共著者であり、Brutalist Web Designのサイトの主でもあります。Javaから入ったキャリアが、この年季の入った感じの出どころかもしれません。

全体は3部に分かれています。導入、Railsの各部分の使い方を細かく論じる本編、そしてRails本体から離れた話（認証と認可、API、CI、監視やログといった運用）です。中心となるのは本編ですが、設計の話だけで終わらせずに運用までひととおり収めているところにも、この本の構えが出ているように思います。開発を続けられるかどうかは、作ったものを動かし続けられるかどうかと切り離せない、ということでしょう。

## 「持続可能」とは何を指しているのか

ところで、タイトルにある「持続可能」が何を指しているのかは、最初に押さえておいた方がよさそうです。

ここで言う持続可能性は、仕様や使えるリソースが増減したり入れ替わったりしても、チームの顔ぶれが変わっても開発を続けられること、とされています。規模や速さの話ではないので、スケーラブルという語は避けたらしいです。言われてみれば、確かにこの2つは別のことですね。規模が大きくなっても捌けることと、来年も直し続けられることは、必ずしも一緒には来ません。

この定義を踏まえると、著者が何に与しないかもはっきりしてきます。著者はクリーンアーキテクチャやSOLIDに与しないことをはっきり示しています。そして、オブジェクト指向らしさ、エレガントさ、再利用、デザインパターン、メトリクスといった言葉で何度も痛い目を見た、と打ち明けたうえで、読みやすさと直しやすさを代わりに掲げます。とはいえ極端な教条に走るわけではなく、どれも引き換えの関係だと繰り返しています。つまり、クリーンアーキテクチャやSOLIDを採らないという話も、それらが間違っているから採らないというより、何かを得れば何かを手放すことになるという前提で選び直した結果、という形になっています。

つまりこの本は、あるべきアーキテクチャを突き詰めるのではなく、目の前の課題を片付けつつシステムを無事に育て、開発を続けられることに重きを置いているわけです。設計の本というと理想形から話が始まることも多いので、ここは最初に分かっておくとよいところだと思います。

Railsに対する態度も同じ調子です。Railsの良さは目一杯認めて寄り添いますが、全面的に従うのではなく、取るものと捨てるものを選んでいます。そして選ぶときに、格好いい手法や新しい手法ではなく、年季の入ったやり方を選んでいます。

## どこでレールから外れるか

では、具体的にどこを取って、どこを捨てているのでしょうか。

レールから外れる箇所の例としては、データの整合性はActiveRecordの検証ではなくDBの制約で担保する、マイグレーションをRubyでなくSQLで書く、ActiveJobを介さずジョブのライブラリを直に使う、コールバックやHelperは用途を絞る、などがあります。こう並べると、だいぶ思い切っているように見えますね。ただ、どれも新しい工夫を持ち込むというより、Railsが用意した仕組みを一段下の素朴なやり方に置き換える方向になっているのが分かります。

そして一番大きいのは、ドメインのロジックの置き場所でしょう。ドメインのロジックはActiveRecordやActiveModelには書かず、サービスクラスとそれを置く層に移します。コントローラやジョブ、メーラからActiveRecordに直接触らないのが原則になります。

なぜモデルから業務のロジックを引き剥がすのか。業務のロジックは複雑で変わりやすく、そういうものが各所から頼られるとバグが重くなりシステムが揺らぐ。一方でActiveRecordのモデルは各所から参照されるのを避けられない。だから分ける、という筋で説明されます。持続可能性の定義から素直につながる話なので、この順で読むと納得しやすいところです。変わりやすいものと、みんなから参照されるものを、同じクラスに同居させない、ということですね。

とはいえ、ActiveRecordを敵視しているわけではありません。associationは書きますし、画面向けと割り切った検証も普通に書きます。結果としてActiveRecordは使い勝手のよいデータアクセスの層として残り、共通化したいクエリもそこに書かれます。

こうなると、ドメインのロジックの層がデータアクセスの層に依存する向きになっていて、クリーンアーキテクチャとは逆、見方を変えればPofEAAの頃へ引き返したような印象も受けます。ただ、Rubyは融通が利くのでそこまで依存の注入に凝らなくてよい、というのは分かる気もします。

## サービスクラスはそんなに大層なものか

サービス層という言葉が出てくると身構える人もいそうですが、この本の言うサービスクラスは結局ただのRubyのクラスで、それを置く場所をサービス層と呼んでいるだけです。Rails標準のクラスだけで粘らず業務のロジックを分けてテストも書こう、共通の親クラスを無理に作らなくてよい、という穏やかな話なので、身構えなくてよいと思います。ただし自由度が高いので、自分たちで規則を作らないと統制が取れないのが難しいところです。

その規則にあたるものとして、本の中のサービスクラスの作法は細かく決められています。クラスメソッドではなくインスタンスを作ってから呼ぶ、callのように何にでも使える名前は付けない、外から全部注入するのではなく必要ならメソッド内で作る、戻り値はそのサービス専用の結果クラスで包む、といった具合です。どれについてもなぜそうするのかをその場で具体的に述べているので、読者は納得できるかどうかで取り入れるかを決められます。これは読む側としてはありがたい書き方です。作法だけを示されると従うか従わないかの話になってしまいますが、理由まで書かれていれば、自分たちの事情に合わせて少し違う決め方をする、という選択もできます。

この結果クラスは、汎用のResult型のようなものを想像すると全然違います。現場で練られた知恵という感じで面白いところです。

同じ調子の細かい方針は他にも並んでいます。例にOpenStructをよく使う、CSSはデザインシステムを前提にOOCSSかユーティリティ系を選ぶ、ログはLogrageで1行にまとめる、テストにはMinitestとFactoryBotを使う、テンプレートはERB、Rakeタスクを1つずつ別ファイルに置く、といったものです。

## どう読むのがよさそうか

ここまで挙げてきたような個々の技法は、それぞれに面白いのですが、この本の読みどころはそこではないように思います。流行りの設計論を避けて、理解しやすさと変更しやすさを優先する、という著者の構えが一貫して通っているところが読みどころです。技法だけを拾って持ち帰ると、なぜそれを選んだのかという肝心な部分が落ちてしまいます。そして、その構えが共有されていない場所に技法だけを持ち込むと、だいたいうまくいかないのではないかと思います。

なので、本の内容を一人で抱えて大改造に走るより、同じチームの人やRails使いの知り合いと読みながら、設計をどうすべきか・なぜそうするのかを話し合うのが一番いい使い方かもしれません。全部に同意できる読者はそう多くないはずで、私自身はマイグレーションをSQLで書くことには賛同していません。そういう引っかかりがあるからこそ、話し合う材料になるのだとも思います。どこに賛成できてどこに賛成できないかを互いに言葉にしていくと、自分たちのアプリで何を大事にしたいのかもはっきりしてくるはずです。
