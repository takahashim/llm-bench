# Rubyのアンチパターン: Hashで何でも表現してしまう

## Rubyアンチパターン: Hashで何でも表現してしまう

Rubyでアプリケーションを開発していると、どうしてもデータの持ち方や設計に悩むことがありますよね。

今回は、特に頻繁に見かける問題点として「Hashを使いすぎる」というものについて、その危険性と対策について考えてみましょう。

### Hashで何でも表現してしまうことの危険性

「Hashは便利だし、JSONとの相性も良いから…」ということで、データをどんなものでもHashに詰め込んでしまっているコードを見かけることがあります。しかし、この書き方にはいくつかの問題点があります。

#### コードの読み解き・変更が重くなる

まず、Hashを使うと何が困るかというと、データの中身が一目で分からないことです。キーを見るだけでは、何を保持しているのかも分かりませんし、それぞれの値の型や意味合いも把握するのに苦労します。

例えば、以下のようなHashを考えてみましょう。

```ruby
data = {
  id: 1,
  name: "Alice",
  age: 30,
  created_at: Time.now
}
```

これだけでは、それぞれの変数が何なのか、何の意味を持っているのか、一目で理解することは困難です。コメントやドキュメントを参照しないと、コードの意図を把握することができません。

また、このHashに対して変更を加えようとしても、どう変更すれば良いのか分かりにくいでしょうか？例えば、`created_at` を更新したい場合、どのように書けば良いのでしょうか？

```ruby
data[:created_at] = Time.now # これでいいの？
```

このように、Hashを使うと、コードの読み解きや変更が重くなるという問題点があります。

#### 凍結しても同じ問題

「Hashを凍結すれば、不変性は保証されるから大丈夫」という意見もあるかもしれません。しかし、Hashを凍結するだけでは、Hash自体の構造や中身が変わらないという保証にはなりません。

例えば、以下のようなコードを考えてみましょう。

```ruby
def process_data(data)
  # ...
end

data = {
  id: 1,
  name: "Alice",
  age: 30,
  created_at: Time.now
}

# 凍結して渡す
process_data(data.freeze)

# しかし、内部でデータのコピーを作成しているわけではないので、
# process_data内でデータを書き換えても元のdataに影響は与えないものの、
# 元のdataは変更される可能性がある。
```

このように、Hashを凍結するだけでは、元のHashがどこかで変更されるという問題点は解決できません。

#### 複雑なクラスでもHashよりマシ

「それなら、Hashを使う代わりに複雑なクラスを作ればいい」という意見もあるかもしれません。しかし、この場合では、Hashに比べて、複雑さが増すという問題点があります。

例えば、以下のようなコードを考えてみましょう。

```ruby
class Data
  attr_accessor :id, :name, :age, :created_at

  def initialize(id:, name:, age:, created_at:)
    @id = id
    @name = name
    @age = age
    @created_at = created_at
  end
end

data = Data.new(
  id: 1,
  name: "Alice",
  age: 30,
  created_at: Time.now
)
```

このように、クラスを作成すると、Hashに比べてコード量が増えますし、メンテナンスも難しくなります。

しかし、この場合では、Hashよりもクラスの方がマシです。なぜなら、クラスの場合は、それぞれの変数の型や意味合いを明確にすることができます。また、インスタンス変数に対して直接アクセスすることを防ぐために、getterとsetterメソッドを作成することもできます。

### Hashを使いすぎないための対策

では、Hashを使いすぎるという問題点を解決するためには、どうすれば良いのでしょうか？

#### 素直にクラスを定義する

まず、データのまとまりをHashで持ち回す癖はやめましょう。素直に専用のクラスを定義して使うのが望ましいです。

「クラスを作るほどでもないな」と感じるなら、`Struct` で代用できます。`Struct` はブロック内にメソッドを書けるので実質的には読み書き用のメソッドが付いたクラスと変わりませんし、RBSでunion typeやinterfaceの宣言など型をはっきり書く準備としても、どんな型を用意すべきかを考えておくのも無駄にならないでしょう。

```ruby
# Structを使う場合
Struct.new(:id, :name, :age).new(1, "Alice", 30)

# keyword_initオプションで初期化メソッドも自動生成できる
Struct.new(:id, :name, :age, keyword_init: true).new(id: 1, name: "Alice", age: 30)
```

#### JSONを扱う場合はクラスを使う

JSONを相手にする処理では、Hashを含むオブジェクトを避けきれない場合もありますが、それでも生のまま持ち回らず、JSONを包むクラスを用意してそのメソッド経由で触る形にした方が楽になります。

```ruby
# JSONからデータを読み込む
data = JSON.parse('{ "id": 1, "name": "Alice", "age": 30 }')

# 生のHashではなく、クラスのインスタンスとして扱う
user = User.new(data)
```

#### Hashを使いすぎているサイン

「それでもHashに頼ってしまう」という場合、以下のような状態になっているかどうか確認してみましょう。

*   **よく似た別物のHashが各所を巡っている**
*   **インスタンス変数をほとんど持たずメソッドの引数のHashに情報を詰めている**
*   **1つのHashでキーの型が混ざっている**
*   **やり取りに使うJSONを加工せず内部処理でも使っている**

これらの状態になっている場合は、Hashを使いすぎているサインです。

#### Hashと共存する場合

上記のような対策をしても、どうしてもHashと共存しなければならない場合もあります。その場合は、

*   キーをシンボルにする
*   値の型を揃える（例えば、数値のみ）
*   キーの名前を統一する（例：`id` でなく `user_id`）

といった対策を行いましょう。

### まとめ

Hashは便利なデータ構造ですが、何でもHashで片付けようとすると、得られる手軽さよりも副作用の方が大きくなります。Hashを使う場合は、上記のような注意点を守り、適切に使い分けるようにしましょう。

**[コード]**
```ruby
# Hashを使った例
data = {
  id: 1,
  name: "Alice",
  age: 30,
  created_at: Time.now
}

# クラスを使った例
class User
  attr_accessor :id, :name, :age, :created_at

  def initialize(id:, name:, age:, created_at:)
    @id = id
    @name = name
    @age = age
    @created_at = created_at
  end
end

user = User.new(
  id: 1,
  name: "Alice",
  age: 30,
  created_at: Time.now
)
```
