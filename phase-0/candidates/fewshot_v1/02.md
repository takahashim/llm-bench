# Rubyのアンチパターン: privateメソッドばかり増やしてしまう

## Rubyアンチパターン：privateメソッドばかり増やしてしまう

「メソッドを細かく割る」「公開範囲を狭める」というアドバイスをそのまま実行し続けると、分割自体は進んでいるのに手に負えない状態に向かってしまうことがあります。

### 問題

以下の状況になっている場合：

*   メソッド数が非常に多い
*   非公開メソッドが公開メソッドよりも圧倒的に多い
*   メソッドのサイズや中身がそろっていない
*   名前の似たメソッドが連なる

### 解決策

解析後のデータが大きくなってきた場合、解析後の値を管理する専用のクラスを立てることも視野に入れましょう。

レポート生成クラスの例：

```ruby
# 不要なメソッドをprivateにするのは問題ありませんが、
# こうすると公開メソッドの数が減りすぎて、
# テストしにくいクラスになってしまいます。
#
# class ReportGenerator
#   def initialize(data)
#     @data = data
#   end
#
#   private
#
#   def parsed_data
#     # ... 解析処理 ...
#   end
#
#   def formatted_data
#     # ... 整形処理 ...
#   end
#
#   def report
#     # ... レポート生成処理 ...
#   end
#
#   def print_report
#     report
#   end
# end

# より良い方法：
class ReportGenerator
  def initialize(data)
    @data = data
  end

  def report
    # ... レポート生成処理 ...
  end
end

class ReportParser
  def initialize(data)
    @data = data
  end

  def parsed_data
    # ... 解析処理 ...
  end
end

class ReportFormatter
  def initialize(parsed_data)
    @parsed_data = parsed_data
  end

  def formatted_data
    # ... 整形処理 ...
  end
end

# 解析、整形、レポート生成の関数をそれぞれ別のクラスに分けることで、
# 役割が明確になり、テストしやすくなります。
```

### 問題点

元のコードでは、`ReportGenerator`クラスに解析処理と整形処理が混ざってしまっています。

### 解決策

解析処理、整形処理、レポート生成処理をそれぞれ別のクラスに分割します。こうすることで、各クラスの役割が明確になり、テストしやすくなります。

このように解析後のデータが大きくなってきた場合、解析後の値を管理する専用のクラスを立てることも視野に入れましょう。
