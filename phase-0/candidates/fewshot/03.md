# Railsアーキテクチャパターン: アプリのリポジトリ内にgemを置く

## Railsアーキテクチャパターン: アプリのリポジトリ内にgemを置く

### 問題点

Railsは融通が利くため、1つのアプリの中で複数のアプリケーションを作成し、それらがお互いに依存しあうような構造になりやすいです。しかし、この形だとそれぞれのアプリが他のアプリに強く依存してしまうため、開発やデプロイが困難になったり、バージョンのずれが生じたりすることがあります。

### 解決策

対象のアプリとだけ歩調を合わせつつ、その機能としては独立したライブラリを作成し、それをそのアプリに含めたgemとして用意することで、アプリケーション間の境界を保ちつつ、普段Gemfileでgemを使っている知識だけで扱えるようにします。

### メリット

*   アプリに頼らないclassやmoduleが一揃いになっている
*   Railsアプリ以外から使う予定はない（むしろいずれ取り外す可能性もある）
*   gemとして扱いたい程度のまとまりがある

このような場合、gemとして切り出すことで、アプリとのバージョンのずれをなくし、普段通りのgemの知識だけで開発やデプロイができるようになります。

### デメリット

*   1〜2ファイル程度で済む機能であれば、わざわざgemにする必要がない
*   他のアプリでも共有したい場合には、別のgemとして作成し、それぞれのGemfileに記述する方が楽である

### Railsという名を冠したRubyアプリケーション全般に適用可能

このパターンは、Railsという名を冠しているとはいえ、gemを前提としたRubyアプリであれば同じように当てはめることができます。

### アプリから見たgemの扱い方

上記のようにして作成したgemは、アプリ側からは普通のgemとして扱えるため、普段Gemfileでgemを使っている知識だけで管理することができます。

### gemとアプリの連携方法

モデルのテストでもコントローラのテストでもない機能単位の検証をgemに付属するtestディレクトリに入れることで、アプリ側はリクエストやシステム単位で書くことになります。同様に、モデルのマイグレーションもアプリ側には含めず、gem側のtest/fixtures/db/migrate/ディレクトリに配置します。

### まとめ

このパターンは、1つのclassやmoduleだけでは収まらない程度のまとまりを、アプリと溶け合って境界を侵さない形で持つことを目的としています。まとまりの大きさによって、ただのRubyライブラリにする場合もRails Engineにする場合もありますが、使う側からは違いなく扱えるようになります。
