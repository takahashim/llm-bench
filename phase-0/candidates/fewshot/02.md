# Rubyのアンチパターン: privateメソッドばかり増やしてしまう

## Rubyアンチパターン：privateメソッドばかり増やしてしまう

「メソッド分割」「アクセス制御」という指針に従ってコードを整理していると、いつの間にかクラスが膨らんでしまい、何かと困るようになります。

### 問題点

このパターンで問題なのは、単純にメソッド数や行数が増えることではありません。以下のような特徴を持つコードになるのが問題です。

*   非公開メソッドの割合が多い
*   メソッドの粒度がそろっていない（小さいものから大きいものまで混在している）
*   名前が似たメソッドが並んでいる

これは、クラス内に毛色の違う役目を持つメソッドを同居させてしまうことに起因します。どのメソッドが何をするのか、何に依存するのかが見えなくなるため、コードの理解や変更が困難になります。

### 対策

このアンチパターンに対応するには、アクセス制御の考え方を少し変える必要があります。「公開範囲を狭める」「メソッド分割」という指針は正しいですが、これらを単純に適用すると、問題が悪化してしまうことがあります。

「メソッド分割」を繰り返すうちに、クラス内で非公開のメソッドばかりが増えていくという状況です。アクセス制御だけでは複雑さは解決しません。なぜなら、アクセス制御はあくまでメソッドへのアクセスを制限するだけで、クラスの内部構造自体には影響がないからです。

この場合、手を入れるべき本当の対象は「これらの処理がすべて同じクラスに同居している」という点にあるはずです。問題点が1つのクラスの中に凝縮されているため、ある箇所を変更すると、どこまで波及するのか見通せなくなってしまいます。

### 具体例

以下のコードは、レポート生成クラスの具体例です。このクラスでは、非公開メソッドはすべて「report」オブジェクトに対して行われます。

```ruby
class ReportGenerator
  private

  def initialize(report)
    @report = report
  end

  def generate_header()
    # ...
  end

  def generate_body()
    # ...
  end

  def generate_footer()
    # ...
  end
end
```

このクラスは、以下の問題を抱えています。

*   レポート生成処理が1つのクラスに同居しているため、どこまで関連するか見えにくい
*   非公開メソッドの割合が高い（7割以上）

### 対策例

このコードを整理してみましょう。まず、レポート生成処理とレポート整形処理は別々の役目であるため、それぞれ別のクラスに分離することにします。

次に、reportオブジェクトを外部から注入したいので、initializeメソッドを公開し、@reportインスタンス変数へのアクセスもprivateにすることにします。

これらの変更により、このクラスの非公開メソッドは不要になります。レポート生成処理はReportGeneratorクラスに、レポート整形処理はFormatterクラスに分割されました。

```ruby
class ReportGenerator
  def initialize(report)
    @report = report
  end

  def generate_report()
    # ...
  end
end

# ...

class Formatter
  def format_header(header_content)
    # ...
  end

  def format_body(body_content)
    # ...
  end

  def format_footer(footer_content)
    # ...
  end
end
```

このように、役目の近いものを束ねて別のクラスに移すと、元のクラスのメソッドも消えてしまうため、「公開したくないメソッドがある」という悩みごともなくなります。

### 関連するアンチパターン

神クラスは、この問題の初期段階で現れやすいものです。神クラスでは、すべての処理が1つのクラスに同居しているため、複雑さが増大します。この場合も、各役目を分離したクラスとして実装することで解決できます。

### その他

また、ある箇所で解析後のデータが大きくなってきた場合は、それ専用のクラスを立てることも視野に入れると良いでしょう。
