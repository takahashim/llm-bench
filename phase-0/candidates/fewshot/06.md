# 『Sustainable Web Development with Ruby on Rails』を読んだ感想

『Sustainable Web Development with Ruby on Rails』を読んだ感想です。

## 読みどころ

この本の良さは個々の技法ではなく、著者の一貫した構えにあると思います。Railsの設計で頭を抱えた経験がある人なら、うなずいたり反発したりしながら楽しめる本になっているかと思います。

## 本書の概要

全体は導入、Railsの各部分の使い方を細かく論じる本編、そしてRails本体から離れた話（認証と認可、API、CI、監視やログといった運用）の3部に分かれています。

## 著者について

著者のGregory BrownさんはStitch Fixでプログラマからアーキテクトまで務めた後に別のスタートアップでCTOを務めているそうです。『Agile Web Development with Rails 6』の共著者であり、Brutalist Web Designのサイトの主でもあります。

https://www.brutalistweb.com/

Javaから入ったキャリアが、この年季の入った感じの出どころかもしれません（個人の感想です）。

## レールからの逸脱

Railsの良さは目一杯認めて寄り添うが、全面的に従うのではなく取るものと捨てるものを選び、格好いい手法や新しい手法ではなく年季の入ったやり方を選んでいるのが本書の特徴です。

著者はクリーンアーキテクチャやSOLIDに与しないことをはっきり示し、オブジェクト指向らしさ、エレガントさ、再利用、デザインパターン、メトリクスといった言葉で何度も痛い目を見たと打ち明けたうえで、読みやすさと直しやすさを代わりに掲げる。極端な教条には走らず、どれも引き換えの関係だと繰り返す。

## サービスクラスの作法

サービスクラスについては細かく方針が定められています。

- クラスメソッドではなくインスタンスを作ってから呼ぶ
- callのように何にでも使える名前は付けない
- 外部から全部注入するのではなく必要ならメソッド内で作る
- 戻り値はそのサービス専用の結果クラスで包む

どれについてもなぜそうするのかをその場で具体的に述べているので、読者は納得できるかどうかで取り入れるかを決められる。

## ドメインロジックの分離

モデルから業務のロジックを引き剥がす理由は、業務のロジックは複雑で変わりやすく、そういうものが各所から頼られるとバグが重くなりシステムが揺らぐ一方、ActiveRecordのモデルは各所から参照されるのを避けられない、という筋で説明される。

この結果クラスは汎用のResult型のようなものを想像すると全然違い、現場で練られた知恵という感じで面白い。

## レールからの逸脱の例

- データの整合性はActiveRecordの検証ではなくDBの制約で担保する
- マイグレーションをRubyでなくSQLで書く
- ActiveJobを介さずジョブのライブラリを直に使う
- コールバックやHelperは用途を絞る

## Railsアーキテクチャについて

Railsの設計で頭を抱えた経験がある人なら、うなずいたり反発したりしながら楽しめる本になっているかと思います。Web開発を長く生き延びてきた人が語る定石、という手触りがあります。

一方でassociationは書き、画面向けと割り切った検証も普通に書くので、ActiveRecordは使い勝手のよいデータアクセスの層として残り、共通化したいクエリもそこに書かれる。ここで言う持続可能性は、仕様や使えるリソースが増減したり入れ替わったりしても、チームの顔ぶれが変わっても開発を続けられること。規模や速さの話ではないのでスケーラブルという語は避けたらしい。

## モデルについて

ドメインロジックの層がデータアクセスの層に依存する向きになっていて、クリーンアーキテクチャとは逆、見方を変えればPofEAAの頃へ引き返したような印象。Rubyは融通が利くのでそこまで依存の注入に凝らなくてよい、というのは分かる気もする。

## その他

Railsアプリケーション設計に関する細かい方針としては、

- OpenStructをよく使う
- CSSはデザインシステムを前提にOOCSSかユーティリティ系を選ぶ
- ログはLogrageで1行にまとめる
- テストにはMinitestとFactoryBotを使う
- テンプレートはERB
- Rakeタスクを1つずつ別ファイルに置く

などが並びます。
