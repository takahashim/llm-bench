# Rubyのアンチパターン: privateメソッドばかり増やしてしまう

## Rubyのアンチパターン: privateメソッドばかり増やしてしまう

メソッド分割やアクセス制御の指針に従ってコードを整理しているのに、クラスが膨らんで困っている、というRuby開発者の皆様へ。

「私メソッド」は、オブジェクト指向プログラミングの基本的な機能であり、クラスの内部処理を隠蔽し、外部からの不正なアクセスを防ぐための手段です。しかし、この機能を使うと、クラスが肥大化してしまうことがあります。

### なぜ私メソッドばかり増やすと、クラスが肥大化するのか？

私メソッドは、そのクラスの内部からのみ呼び出すことができます。したがって、同じクラス内であれば、互いに自由に私メソッドを呼び出すことができます。これは、アクセス制御の仕組み上、止めることはできません。

しかし、私メソッドを増やしすぎると、そのクラスが複雑になります。行数とメソッド数がふえてしまう、非公開のものが公開のものより圧倒的に多い、ひとつひとつの大きさや中身がそろっていない、名前の似たものが連なる、といった問題が生じます。

### 具体的な例

例えば、レポートを生成するクラスがあったとします。このクラスには、レポートのデータを作成するメソッドと、レポートを生成するメソッドがあります。

```ruby
class ReportGenerator
  private

  def data # データ作成
    # ...
  end

  def parsed_data # 解析済みデータ作成
    # ...
  end

  def generate_report # レポート生成
    # ...
  end
end
```

この例では、`data` と `parsed_data` が別の値なので、それぞれの中身に踏み込むメソッドは互いに縁が薄いです。したがって、これらのメソッドを同じクラスに置く理由がありません。

### どのようにすれば良かったのか？

メソッド分割やアクセス制御の指針に従ってコードを整理しているのに、クラスが肥大化してしまうのはなぜでしょうか？それは、メソッドを細かく割る・公開範囲を絞るという助言をそのまま実行し続けているからです。

メソッドを細かく割ること自体は正しい方向性であり、クラスの内部処理を隠蔽することも重要ですが、分割自体は進んでいるのに手に負えない状態へ向かってしまうことがあります。

### 具体的な解決策

この問題を解決するには、メソッドを同じクラスに同居させないようにします。役目の近いものを束ねて別のクラスへ移してしまえば、元のクラスからそのメソッドが消えるので、公開したくないものを抱えているという悩み自体がなくなるはずです。

例えば、レポート生成クラスの場合、以下のようにクラスを分割することができます。

```ruby
class ReportGenerator
  def generate_report # レポート生成
    # ...
  end
end

class ReportData # レポートデータの生成と解析
  def data # データ作成
    # ...
  end

  def parsed_data # 解析済みデータ作成
    # ...
  end
end
```

さらに、解析後のデータが大きくなってきた場合は、それ専用のクラスを立てることも視野に入れて良いでしょう。

```ruby
class ReportGenerator
  def generate_report # レポート生成
    # ...
  end
end

class ReportData # レポートデータの生成と解析
  def data # データ作成
    # ...
  end

  def parsed_data # 解析済みデータ作成
    # ...
  end
end

class Report # レポート
end
```

また、抽出先を内側に入れ子にすると、より簡潔に記述できます。

```ruby
class ReportGenerator
  def generate_report # レポート生成
    # ...
  end
end

class ReportData < ReportGenerator # レポートデータの生成と解析
  def data # データ作成
    # ...
  end

  def parsed_data # 解析済みデータ作成
    # ...
  end
end

class Report < ReportGenerator # レポート
end
```

### その他にも

このように、クラスを分割することで、以下のようなメリットがあります。

*   よく似た処理を他の場所でも使いたくなったときに丸ごと写すことができるようになる。
*   同じクラスの中でも似通ったコードが繰り返されることを防ぐことができる。
*   レポートの種類ごとに異なるデータ構造を持たせることができる。

### 近い種類のアンチパターン

「私メソッドばかり増やす」という状況は、神クラスというアンチパターンにも似ています。

神クラスは、あらゆる処理を1つのクラスで行ってしまうことです。この場合、そのクラスが複雑になり、手を入れるべき本当の対象は、それらが1つのクラスに同居していることだと著者は捉えています。

### まとめ

メソッドを細かく割る・公開範囲を絞るという助言をそのまま実行し続けると、分割自体は進んでいるのに手に負えない状態へ向かってしまうことがあります。クラスを分割する際には、メソッドの役目と、それに対応するデータの持ち方を考慮するようにしましょう。
