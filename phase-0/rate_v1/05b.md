# tailwindcss-railsが今の形に落ち着くまで

# 題
tailwindcss-railsが今の形に落ち着くまで
# 読者
Rails 7でTailwind CSSを使いたいRuby/Rails開発者
# 主張
Node.jsに頼らないというRails 7の方針とTailwind CSSのv3でのJIT必須化は一度ぶつかったが、Tailwind側が単体で動くCLIを出したことで解消し、Tailwind CSS for Railsは安心して頼れる道具になった。
# 要点
- 12月17日にはTailwind公式がStandalone CLIを打ち出し、RailsやPhoenixといったnpmを前提としない環境でも、性能を落とさず使えるようにした。
- ReactやVueの広まりでCSSの命名規則にコンポーネントの事情を背負わせなくてよくなり、不要な定義を削る仕組みで本番のCSSを小さくできるようになった流れもあって、好き嫌いや現場の都合はあれど一定の支持は得ているのではないか。
- 新規作成時はrails newにtailwind指定のオプションを渡すだけで入り、既存アプリならGemfileに追記してbundle installしたうえでrailsコマンドから導入する。起動後はerbを保存するたびにJITが走る様子がアクセスログに出る。(コード)
- tailwindcss-railsはDHHが2021年1月に着手したgemで、v1.0.0の正式版が出たのは日本時間で12月15日、その翌日にRails 7が公開されている。
- Tailwind CSSはUtility-Firstを掲げるCSSフレームワークで、見た目の指定がそのままタグのclass属性に長々と並ぶ。
- Standalone CLIが内部で使っているpkgはVercel製で、Node.jsのフロントエンド文化を引っ張ってきた会社がNode.js抜きの環境づくりにも効いているのは、思いがけない巡り合わせだと感じた。
- 12月10日に出たTailwind CSS v3.0ではv2.1で入ったJITエンジンが既定となり、Node.jsなしでは実際上使いにくいものになっていた。
- それ以前にTailwindをRailsへ持ち込む手立ては、WebpackerやSimpackerと組んでnpmで入れる、フロントエンド側のフレームワークに任せてRails側は手を出さない、CDN上のものを読む、といったあたりだった。
- Standalone CLIの実体はJITエンジンをNodeの処理系ごと1本の大きなバイナリに固めたもので、RubyのExerbやTraveling Rubyに近い。素直にNode.jsを使っているじゃないかと言いたくもなるが、npm周りの作業が消えるのは確かに楽。
- これまでのCSS設計の定石とはほぼ逆を向いており、OOCSSやBEMを使いこなしてきた人ほどHTMLに埋め込まれた記法に面食らっていたようだ。
- 出てきた当初は便利そうでも強引さを感じ、かつてRailsで流行っては消えたJSをgemで包む手法も頭をよぎった。それがStandalone CLIの出現で、安心して使えるものに生まれ変わったように見える。
- そのため12月15日のv1.0.0はTailwind CSS v2.1向けという位置づけで、v3を今すぐ使いたければcssbundling-railsと組み合わせてNode.jsに頼るしかなかった。
- Rails 7はConceptual Compressionを押し進め、Node.jsなしでもRails自身で片が付くように新しいgemの整備が進められてきた。
- 今後は仕組みから考えて、Tailwind CSS本体の更新に追従する形でこのgemもリリースされていくと見られる。
- Railsのテンプレートでコンポーネントを扱う場合は、このところはViewComponentが選ばれていることが多い印象。
- ところが12月20日の時点では、このgemはv2.0.2まで進んでいて、短い間に状況が大きく動いた。
- Node.jsに頼る状態はRails 7の方針と噛み合わず、それならgemを独立させた意味がなかったのでは、という話になりかねなかった。
- 12月18日にCLIを取り込む変更が入り、同じ日に2.0.0が公開された。v1.0.0にあった不要なCSSを削るRuby側の処理は、CLIに任せられるので丸ごと取り除かれた。
