# 『Sustainable Web Development with Ruby on Rails』を読んだ感想

『Sustainable Web Development with Ruby on Rails』を読んだ感想です。

## 読みどころ

この本の読みどころは個々の技法ではなく、流行りの設計論を避けて理解しやすさと変更しやすさを優先する著者の一貫した構えにあると思います。全部を真似る必要はなく、仲間と設計を論じ合う材料として読むのがよいです。

## 著者について

著者のBen Schneiderman氏はStitch Fixでプログラマからアーキテクトまで務めた後に別のスタートアップでCTOを務めているそうです。また、『Agile Web Development with Rails 6』の共著者であり、Brutalist Web Designのサイトの主でもあります。Javaから入ったキャリアが、この年季の入った感じの出どころかもしれません。

## 内容について

全体は導入、本編、Rails本体から離れた話（認証と認可、API、CI、監視やログといった運用）の3部構成になっています。Railsの設計で頭を抱えた経験のある人なら、うなずいたり反発したりしながら楽しめる本で、Web開発を長く生き延びてきた人が語る定石、という手触りがあります。

## レールから外れるところ

Railsの良さは目一杯認めて寄り添うものの、全面的に従うのではなく取るものと捨てるものを選び、格好いい手法や新しい手法ではなく年季の入ったやり方を選んでいます。レールから外れる箇所の例としては、データの整合性はActiveRecordの検証ではなくDBの制約で担保する、マイグレーションをRubyでなくSQLで書く、ActiveJobを介さずジョブのライブラリを直に使う、コールバックやHelperは用途を絞る、などがあります。

## サービスクラスについて

ドメインのロジックはActiveRecordやActiveModelには書かず、サービスクラスとそれを置く層に移します。コントローラやジョブ、メーラからActiveRecordに直接触らないのが原則です。また、モデルから業務のロジックを引き剥がす理由は、業務のロジックは複雑で変わりやすく、そういうものが各所から頼られるとバグが重くなりシステムが揺らぐ一方、ActiveRecordのモデルは各所から参照されるのを避けられない、という筋で説明されます。

## サービスクラスを置く層について

このサービスクラスは結局ただのRubyのクラスで、それを置く場所をサービス層と呼んでいるだけです。Rails標準のクラスだけで粘らず業務のロジックを分けてテストも書こう、共通の親クラスを無理に作らなくてよい、という穏やかな話なので身構えなくてよいです。ただし自由度が高く、自分たちで規則を作らないと統制が取れないのが難しいところです。

## その他

細かい方針としては、例にOpenStructをよく使う、CSSはデザインシステムを前提にOOCSSかユーティリティ系を選ぶ、ログはLogrageで1行にまとめる、テストにはMinitestとFactoryBotを使う、テンプレートはERB、Rakeタスクを1つずつ別ファイルに置く、といったものが並びます。モデルのassociationは書き、画面向けと割り切った検証も普通に書くので、ActiveRecordは使い勝手のよいデータアクセスの層として残り、共通化したいクエリもそこに書かれます。

## まとめ

この結果クラスは汎用のResult型のようなものを想像すると全然違い、現場で練られた知恵という感じで面白いです。あるべきアーキテクチャを突き詰めるのではなく、目の前の課題を片付けつつシステムを無事に育て、開発を続けられることに重きを置いているのがよいです。『Sustainable Web Development with Ruby on Rails』は、Railsの設計で頭を抱えた経験のある人には特にお勧めできる本です。
