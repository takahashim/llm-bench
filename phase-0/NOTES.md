## 2. 途中で起きたこと

**固有名を伏せていた。** 最初に終わった担当（28〜36）が、漏洩率を下げるために
GDB を「GNU 製デバッガ」、Homebrew を「パッケージ管理の仕組み」、mbed を
「この基板向け開発環境」と書いていた。漏洩率は 0.0% だったが、生成側は要点に無い
名前を書けないので、これは捏造か曖昧な文を教える学習データになる。
原因は `EXTRACT.md` に「固有名はそのまま書く」が無かったこと。規則を足して 4 担当に
送り、全員が書き直した。28〜36 で戻した固有名は 145 個。

教訓: 「原文の言い回しを写さない」と「原文に無いことを足さない」の間に、
「原文の名前は落とさない」が要る。前者だけを強く言うと、後者を犠牲にして指標を
満たしにくる。Phase -1 では偶然起きなかった（Hash・Struct・RBS は一般語に言い換え
ようがなかった）。

**漏洩の測り方を変えた。** 固有名をそのまま書くと、識別子の密な記事（mbed の
ツールチェイン名、mrbgem 名、`-Dexec.mainClass` など）は 10-gram の生の一致率が
5% を超える。これは言い回しの写しではない。`check_facts.py` は ASCII の並びを
除いた一致率（`ja` 列）で判定し、生の値（`leak` 列）は併記する。
`phase-1/check_leakage.py` は変えていない（Phase -1 の数字との比較のため）。

**thesis の一致。** 3 本で thesis に原文と一致する 10-gram があったが、いずれも
用語（「開発抽象化レイヤー」「ボイラープレート」「キーチェーンアクセス」）。
不合格にはせず表示のみ。

## 5. Phase 0a 学習(2026-11-09、bear1 CPU)

| | |
|---|---|
| base | Llama-3.1-Swallow-8B-Instruct-v0.5、bf16(4bit にしない。16GB が載る) |
| LoRA | r=16、alpha=32、q/k/v/o/gate/up/down、41.9M params(0.52%) |
| データ | train 33 本(82,358 tok/epoch、1 本が 8192 で切られた)、val 3 本 |
| 学習 | 3 epoch、15 step(batch 1 × accum 8)、lr 2e-4 cosine、本文のみ loss |
| 速度 | **18.6 tok/s**(gradient checkpointing あり)。机上の 46 tok/s の 4 割 |
| 時間 | **4 時間 0 分** |
| val loss | 1.567 → 1.339 → 1.193 → **1.194**(epoch 2 で下げ止まり) |

Vulkan は学習に使えない(llama.cpp の finetune は FP32 全パラメータのみ、PyTorch に Vulkan
学習バックエンド無し)。CPU は Zen4 の AVX-512 BF16 で bf16 行列積 1.7 TFLOPS(fp32 の 2.4 倍)。

生成は adapter を merge → GGUF(Q8_0、7.95 GiB)→ bear1 の iGPU(Vulkan)。few-shot 対照は
同じ base を同じ経路で Q8_0 にしたもの。llm-jp の推論サーバ(21GB)は GTT 30GiB に同居
できないので止めた。

## 6. v1 生成の観察 → 反復抑止で v2 を作り直し

v1(temperature 0.7、top_p 0.9、repeat_penalty 1.05)の 20 本を著者に渡す前に検査した。

**反復が多い。** 同一文の重複が LoRA 版で 02: 49、06: 121、07: 49、09: 18。few-shot 版でも
02: 19、08: 39(3,000 トークンの上限に達した)。LoRA 06 は `[コード]` と書いた直後に
Ruby のコードを 5,000 字出し続けた。few-shot 10 は 210 字で止まり、存在しない URL を 2 本
書いた。これでは評価が反復の有無の評価になるので、**両条件とも同じ反復抑止
(DRY 0.8、repeat_penalty 1.1)で v2 を生成し直した。** v1 は `candidates/*_v1`、`rate_v1/` に残す。

**捏造(事実リストに無い数値・英数字トークン)。** LoRA 132 件(うち 76 は 06 のコード)、
few-shot 100 件。Opus(Phase -1)は一般語 5 件だった。8B はどちらの条件でも桁違いに
多く、SPEC の「捏造 0 必須」は両方とも満たさない。

**評価用原文への漏洩(10-gram)。** LoRA 0〜7.4%、few-shot 0〜7.7%。Opus は平均 2.4%。
どちらも評価用の原文は見ていない(LoRA の学習データにも無い)ので、Swallow の事前学習に
Zenn/Qiita が入っている可能性と、事実リスト自体の漏洩(0.2〜5.1%)の継承の両方がありうる。
few-shot の方が高いのは、手本 3 本(著者の記事)の言い回しを写すため。

**文体の指標(1000字あたり)。**

| | かと思います | と思います | かもしれません | 文数 | 箇条書き行 | 見出し |
|---|---|---|---|---|---|---|
| 原文 10 本 | 0.4 | 0.1 | 0.5 | 9.9 | 6.3 | 3.0 |
| LoRA v1 | 0.0 | 0.0 | 0.2 | 4.9 | 3.0 | 4.9 |
| few-shot v1 | 0.1 | 0.9 | 0.5 | 11.3 | 1.9 | 7.1 |
| Opus few-shot(Phase -1) | 0.2 | 0.6 | 0.6 | 14.7 | 2.0 | 2.6 |

LoRA 版の文数が少ないのは反復とコードで字数が膨れたため(v2 で見直す)。few-shot 版は
手本から「と思います」を過剰に拾う。

## 7. 手順上の失敗

- `pkill -f` / `pgrep -f` のパターンが自分のシェルのコマンド行に一致して自分を殺す(exit 144)
  を 3 回やった。パターンは `'[l]lama-server'` のように先頭を文字クラスにする
- llama-server の `dry_penalty_last_n: -1` は b12201 では 400(0 以上のみ)。省略すれば既定が使われる

## 8. v2 生成(DRY 0.8、repeat_penalty 1.1)の観察 → これを評価に出す

生成時間: LoRA 版 10 本 23 分、few-shot 版 10 本 22 分(iGPU、Q8 8B、9.7 tok/s)。

| | LoRA v2 | few-shot v2 |
|---|---|---|
| 散文の重複文(コードを除く) | 02: 48、03: 14、07: 11、他 ≤ 7 | 全件 ≤ 7 |
| 崩壊 | **06**(散文 75 字 + コード)、**08**(113 字。題を繰り返して捏造 URL 1 本で終了) | なし |
| コードブロック | 7/10 本に出る(02 は 19 個、5,688 字) | 4/10 本 |
| 上限 3,000 tok 到達 | 02 | なし |
| 捏造トークン(数値・英数字、事実リスト外) | 198 | 233 |
| 原文への漏洩(10-gram) | 0.0〜6.0% | 1.0〜5.6% |
| 文体: かと思います / かもしれません(1000字) | 0.0 / 0.1 | 0.1 / 0.5 |

DRY は散文の反復には効いた(v1 の 49〜121 → 最大 48)が、コードの反復には効かず、
LoRA 版はコードを書く癖が強くなっている。指示は「コードは [コード] と書く」で、
学習データの本文も `[コード]` 置換済みなのに、LoRA 版は実コードを出す。
`[コード]` の位置を「ここにコードが入る」と学び、生成時はそれを実コードで埋めている
と見える。few-shot 版も手本の `[コード]` を見て 4 本でコードを書いた。

v1 → v2 でサンプラを変えたのは両条件に同じで、片方だけを有利にしていない。
これ以上サンプラを触るのはやめ、**v2 を評価に出す。** 崩壊した 06・08 は D になるが、
それは 33 本の LoRA がモデルを不安定にしたという結果そのものである。

著者に渡すもの: `rate/form.md`(20 本、a/b はランダム)。`rate/key.json` は開かない。

## 9. 著者の評価（2026-11-09）と目標の訂正

著者は 20 本を採点せず、所感で答えた: **「自分の書き方に寄っているかは評価しなくていい。
独自の文体でも構わない。ただ概ね一文が短く、読むための文章としては評価が低いものが多い。
ストーリーが読み取りにくいか、存在しない」**。条件（LoRA / few-shot）は問わず。

これは評価結果であると同時に目標の訂正である（SPEC 1 節）。文体の一致は目標ではなく、
「読者が筋を追える文章」が目標。

表面指標で「筋の無さ」を捉えようとしたが、捉えられなかった:

| 条件 | 入力順への追従(相関) | 文の平均字数 | 文頭の接続表現/文 |
|---|---|---|---|
| 原文 | 0.35（シャッフル済み要点との照合の雑音床） | 44.1 | 0.05 |
| Opus few-shot | 0.32 | 42.1 | 0.09 |
| LoRA v2 | 0.34 | 37.1 | 0.08 |
| few-shot v2 | 0.36 | 46.2 | 0.06 |

要点の順に書いているわけではなく（原文と同じ水準）、文も極端に短くはない。
「筋」は文の長さや順序ではなく、論の運び（問い → 根拠 → 結論、譲歩、限界）の有無で、
これは Phase -1 で工程 B として捨てたものに近い。入力（事実 + thesis）にも 8B にも無い。
